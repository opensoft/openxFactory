# Factory MCP advisory conformance

Status: draft
Kind: runbook
Governed by: [add-factory-mcp-conformance](../openspec/changes/archive/2026-10-06-add-factory-mcp-conformance/proposal.md), ratified 2026-09-07; amended by [amend-factory-mcp-conformance-auth-profile](../openspec/changes/amend-factory-mcp-conformance-auth-profile/proposal.md), ratified 2026-10-08 (the hosted authorization block, the narrowed *Unavailable dependency* scenario and per-domain error vocabularies)

The unreleased [declaration schema](../contracts/factory-mcp/declaration.schema.json) and [validator](../scripts/validate-factory-mcp.py) check a domain's declared contract offline. They report structural validity, reference integrity, semantic consistency and unresolved gaps separately. Even a valid declaration returns `verified_conformance: false`: source citations still require behavioral review and deployment acceptance.

## Run the synthetic example

From the repository root inside py-bench (Python 3.12 and jsonschema 4.25.1 were used):

```sh
python3 scripts/validate-factory-mcp.py \
  contracts/factory-mcp/examples/declaration.example.json \
  --snapshot synthetic@aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa=contracts/factory-mcp/examples \
  --json
python3 scripts/validate-factory-mcp.py \
  contracts/factory-mcp/examples/declaration-deployed.example.json \
  --snapshot synthetic@aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa=contracts/factory-mcp/examples \
  --json
python3 -m unittest discover -s tests/factory-mcp -v
python3 -m pytest tests/factory-mcp -q
```

The expected status is `valid-with-gaps` because the synthetic example has no resolving audit sink. The deployed example, the same declaration with its service deployed and an authorization block, is `valid-with-gaps` as well: it also reports `auth-gap`, because no server's token verification was observed for a synthetic block. Run the tests in an environment built from `requirements/hermes-runtime-contracts.lock` with `--require-hashes`, as CI does. An optional URI format-checker package the lock does not carry makes four existing reference tests report `invalid_json_schema` instead of their expected codes. Its revision is an explicit synthetic snapshot identifier, not a claimed Git commit. Caller-supplied snapshot roots must be trusted immutable copies; matching file digests establishes supplied-byte integrity, not who produced those bytes or whether a repository actually accepted them.

## Declaration and diagnostics

The root, every nested record, identifiers, modes and authority fields are closed. A tool `id` is one token of ASCII letters, digits, `_`, `.` and `-`, at most 80 characters. Tools name their owning domain; schemas have repository/revision/path/SHA-256 references, and a tool's input, output and error schemas come from the repository and revision that `source` names (`tool_schema_outside_source`). A deployed service's `canonical_resource_uri` is an absolute `https` URI made only of the characters RFC 3986 allows unescaped (an internationalized host is written in its ASCII form; `{`, `}`, `|`, `^`, a backtick, `<`, `>`, `"` and the backslash must be percent-encoded), with a host, well-formed percent escapes (`%` followed by two hexadecimal digits), `[` and `]` only around an IP-literal host, and no userinfo or fragment. This holds whether or not the optional format checker is installed. Evidence and gap IDs are unique and concern-tagged; tools must reference support for binding, effects, outcomes, evidence, repetition and limits, and a deployed service's authorization block must reference support for `auth` (see below). Scope gaps, missing revocation and unimplemented audit sinks cannot masquerade as implemented claims: a `mapped` scope that cites a scope gap is refused (`mapped_scope_claims_gap`).

Effects distinguish external reads, execution, persistence and target mutation. This profile fixes authority to none and target mutation to false. Execution requires a bounded trusted-host declaration. These are checked declarations, not enforcement of the described implementation.

Outcome inventories point to string enum/const nodes, including local references and oneOf/anyOf finite unions. An inventory must be reachable from its schema's root through the subschemas a 2020-12 evaluator applies to an instance (`unreachable_inventory` otherwise), so an unused `$defs` entry, or a subschema under `not`, `if`, `contentSchema` or a pre-2020-12 keyword, cannot stand in for the outcome; reachability is checked before the vocabulary is read. Neither can a subschema under `then` or `else`: they apply only beside an `if`, and conditional coverage is not modeled. A boolean schema is known by its place, so a reachable `true` is a reachable inventory with an unbounded vocabulary (it needs a gap) while an unused `true` definition stays unreachable. Under `oneOf` a value counts only when exactly one branch accepts it; a node carrying both `oneOf` and `anyOf`, an `enum` or `const` beside a union, or a `type` that excludes strings (checked before a `$ref` or union is followed) is unresolved and needs a gap. When a domain lists its outcomes as a union of object branches, each carrying its code in a property (for example `oneOf` error objects with `properties.code.const`), the inventory points at the union, or at a `$ref` to it, and names that property as its optional `discriminator`. The vocabulary is then the union of every branch's constant or enum for that property, following `$ref`. Under `oneOf` the branches must not share a value: an object matching two branches matches none, and object branches can share a code while differing elsewhere, so a shared code makes the inventory unresolved. Each branch must be object-only (`type: object` on the branch or on an enclosing union), list the property in `required`, and constrain it to strings, or the inventory is unresolved. Along the union, its `$ref` links and its branches, the projection reads only `type`, `required`, `properties`, `additionalProperties`, `$ref`, `oneOf`, `anyOf`, annotations, core metadata and `$defs`. Any other keyword there, such as `dependentRequired` or `unevaluatedProperties`, could leave a branch no instance, so it leaves the inventory unresolved. So does `properties` on an enclosing union. Every name a branch requires must also be admissible. A closed schema (`additionalProperties: false`, directly or through `$ref`) on the branch or an enclosing union admits only the names its own `properties` declares. An `additionalProperties` schema that asserts anything else is not analyzed. A required property's own schema is judged only at its top level, along its `$ref` chain. `false` holds no value. `not`, `if`/`then`/`else`, `allOf`, `oneOf` or `anyOf` there is not analyzed. `type`, `const` and `enum` apply together across every link, so a contradiction among them (such as `type: object` with `const: false`) holds no value. Values compare as JSON does, at any depth: `[1]` equals `[1.0]`, and `true` never equals a number. Each of these makes the inventory unresolved. Constraints deeper inside a required property are outside this offline check. Mapping entries must exhaust each finite inventory without duplicates and preserve the correct completed-evaluation/execution-failure and isError classification: a value of a result inventory is a completed evaluation with `is_error: false`, and a value of an error inventory an execution failure with `is_error: true` (`outcome_classification_mismatch` otherwise). So a domain that cannot evaluate because a dependency is unavailable reports that through its error inventory, and the mapping then names an execution failure and never eligibility. A result status is a completed evaluation whatever its name says; what a result status means stays the domain's. Unsupported narrowing constraints (among them `allOf`, `not`, conditionals, string patterns and lengths, and object cardinality or property-name constraints such as `minProperties`, `maxProperties` and `propertyNames`, which can leave a branch no instance), cycles or unbounded vocabularies require an explicit outcomes gap. Missing pointers are errors, and pointers follow RFC 6901 strictly: an array index is `0` or a digit run with no leading zero, and `~` escapes only `~0` and `~1`.

Error vocabularies stay per domain. Each domain keeps its own codes and envelope in its own published schemas, and the profile defines no neutral error-code list and requires no published schema to change. The lossless mapping (each code's class and isError semantics, with the domain object unchanged in structuredContent) is the only layer the domains share. The validator reads each declaration's codes from that declaration's own pinned schema and never compares declarations, so a code name two domains both use carries no shared meaning or retry semantics, and a code no other domain uses is judged by its own mapping alone.

An inventory inside one member of a union, such as one result variant or one constant of a code union, maps only that member. Every other member of that union must then hold an inventory on the same schema file, or the tool's schema is reported `uncovered_outcome_branch`. Membership is judged by reachability through `$ref`, never through `not` or `if`, so a definition that every variant references covers them all, and a single file cited as both output and error is covered by its result and error inventories together. A `false` member, or one that reaches `false` through a `$ref` chain (a `$ref` applies beside its siblings), needs no inventory. A `true` member, or a chain of pure references (a `$ref` beside only annotations, core metadata such as `$id` and `$schema`, or `$defs`) ending in `true`, cannot hold one and needs a declared outcomes gap on that schema; a constraining keyword anywhere on such a chain leaves the member needing an inventory. Holding is propagated once from the inventories over the file's reference graph, and each `$ref` chain's end is memoized link by link, so coverage stays linear in the schema's size however its references are shared. Each distinct schema file's reference graph is checked once, however many tool fields cite it. A domain output stays verbatim in structuredContent; the declaration never inserts a wrapper into a digested object.

Repetition selects exactly one of reevaluate, lease_replay or fresh_observation. Replay requires persistence, principal-scoped keys, explicit conflict/in-progress handling, coordination and preserved timestamps. Fresh observation requires external reads, observation timestamps, host-controlled age limits and a final age check. Trace IDs are never grants or implicit replay keys.

Reports contain `status`, `exit_code`, `checks`, `diagnostics`, `gaps` and `verified_conformance`. Each diagnostic has a stable code, dimension and JSON-pointer location in the declaration: a reference failure names the citation that failed (for example `/tools/0/input` or `/source/artifacts/0`), and a semantic finding names the field to fix. Identical diagnostics are reported once. Checks that could not run are null, not passed. Diagnostics sort by dimension, location and code. Exit 0 means valid or valid-with-gaps; 1 means an invalid declaration, including malformed or oversized input (`malformed_json`, `duplicate_json_key`, `non_json_number`, `json_number_limit` for an integer past Python's digit limit or a number literal that overflows to infinity (`1e9999`) or a nonzero one that underflows to zero (`1e-9999`), in the declaration or in any referenced schema, `input_size_limit`); 2 means unreadable input or unavailable/unreadable reference roots, a rendered report past the output bound (`output_size_limit`), and also a command-line usage error such as a malformed `--snapshot`. Human output also prints every explicit gap. Declaration text in human output has control, format and separator characters (and the backslash) escaped, so a declaration cannot add lines or terminal sequences; `--json` output is JSON-escaped.

## Hosted authorization block

A deployed service declares the tokens its server accepts in an `auth` block beside `canonical_resource_uri`, which is the protected resource the block describes. A service that is not deployed is reached only over stdio by a host that launches it, takes its credentials from its environment, and carries no block: its closed schema branch refuses one (`schema_oneOf` at `/service`). The block is closed and holds exactly six fields, and none can hold key material, a client secret or a token; the server finds keys in its issuer's published metadata.

```json
"auth": {
  "issuer": "https://issuer.example.test/synthetic",
  "algorithms": ["RS256", "EdDSA"],
  "audience": {"binding": "resource_uri", "value": "https://mcp.example.test/mcp"},
  "metadata_path": "/.well-known/oauth-protected-resource/mcp",
  "evidence_ids": [],
  "gap_ids": ["auth-gap"]
}
```

- **Issuer**: one absolute `https` issuer identifier with a host, under the same character rules as the canonical resource URI, and without query, fragment or userinfo. A runtime or product name is refused.
- **Algorithms**: RS256 is required, EdDSA may be added, and nothing else is admitted. `none`, `HS256`, `HS384` and `HS512` are refused by name in any letter case. Every other name, including `rs256` (algorithm names are case-sensitive), is not admitted; admitting one is a governed change to the profile.
- **Audience**: exactly one value the server requires as the token's `aud`. A `resource_uri` binding names exactly `canonical_resource_uri`. An `issuer_assigned` binding names an identifier the issuer assigned to this resource alone, such as an application identifier; it rests on the block's cited evidence or gap and is never certified. No audience contains `*` or equals the issuer. Each declaration is validated alone, so a shared audience across two domain servers is not detectable offline.
- **Metadata path**: the RFC 9728 section 3.1 location, `/.well-known/oauth-protected-resource` followed by the canonical resource URI's path as written, unless that path is empty or `/`. So `https://mcp.example.test` gives `/.well-known/oauth-protected-resource`, and `https://mcp.example.test/mcp` gives `/.well-known/oauth-protected-resource/mcp`. A deployed service's canonical resource URI carries no query, since a path field cannot represent one.
- **Support**: the block's `evidence_ids` and `gap_ids` resolve exactly as a tool's do, and at least one resolved record carries the `auth` concern. A block supported only by a gap is `valid-with-gaps`.

| Code | Location | Condition |
| --- | --- | --- |
| `hosted_auth_missing` | `/service` | a deployed service has no `auth` |
| `schema_oneOf` | `/service` | a not-deployed service carries `auth`, or the block breaks its closed shape (an unknown field, a wrong type, a binding outside `resource_uri` and `issuer_assigned`, an empty or repeated algorithm list, more than one issuer); the structure pass does not descend into `service`'s branches, so it cannot name the field |
| `invalid_issuer` | `/service/auth/issuer` | not an absolute https identifier with a host, or it carries a query, fragment or userinfo |
| `auth_rs256_missing` | `/service/auth/algorithms` | RS256 is not listed |
| `auth_algorithm_forbidden` | `/service/auth/algorithms/<k>` | `none`, `HS256`, `HS384` or `HS512`, in any letter case |
| `auth_algorithm_unadmitted` | `/service/auth/algorithms/<k>` | any other value than `RS256` or `EdDSA` |
| `auth_audience_unbound` | `/service/auth/audience/value` | a `resource_uri` binding names anything but `canonical_resource_uri`, or any audience contains `*` or equals the issuer |
| `auth_metadata_path_mismatch` | `/service/auth/metadata_path` | not the RFC 9728 section 3.1 location; not compared while the URI itself is `invalid_resource_uri` |
| `auth_resource_query` | `/service/canonical_resource_uri` | a deployed service's canonical resource URI has a `?` before any `#`, even an empty query, with or without a block |
| `unsupported_auth` | `/service/auth/evidence_ids` | no cited evidence or gap carries `auth` |
| `duplicate_support_reference` | `/service/auth/evidence_ids` or `/service/auth/gap_ids` | an id is repeated within one list |
| `missing_support_reference` | `/service/auth/evidence_ids/<k>` or `/service/auth/gap_ids/<k>` | a cited id matches no evidence or gap record |

These checks run in the semantic pass, after structure and references, in the existing dimensions and order. Like every other field, the block is a declaration checked offline: a valid block certifies neither that a server verifies signatures, finds keys or checks expiry, nor that it enforces the audience.

## Offline reference boundary

Supply one `--snapshot repository@full_revision=root` per immutable snapshot. Every referenced file, including cross-file JSON Schema references, needs a digest-bearing artifact citation. Paths must be normalized relative paths contained under the supplied root. Absolute paths, traversal, URI paths, escaping or looping symlinks, missing artifacts and mismatched digests refuse. The validator never fetches schema resources or executes schema content.

Local fragment pointers and pinned local file references are supported. A `$ref` fragment is strictly percent-decoded before it is read as a JSON Pointer or told apart from a named anchor (so `#%2Fa` is the pointer `/a`), so `:`, `?` and well-formed escapes may select keys; a malformed escape is `invalid_pointer`. A scheme, an escape or a query in the path part, or a second `#`, is refused. A subschema carrying its own `$id` is an embedded schema resource, as JSON Schema 2020-12 defines it: a fragment reference inside it resolves against that resource, not the document root, and only a relative non-fragment reference inside it is refused (`relative_reference_in_embedded_resource`). The analysis applies JSON Schema 2020-12 semantics, so a schema object declaring any other `$schema` dialect, at the root, under a nested `$id` or elsewhere, is refused (`unsupported_schema_dialect`). This includes the root of a file reached only through a fragment reference, and any resource that a reference's pointer passes through. A schema without `$schema` is read as 2020-12. Non-fragment references under a root schema base URI (`unsupported_schema_base_uri`), dynamic/recursive references and named anchors are conservatively refused; ordinary recursive fragment schemas are supported. A root schema ID is metadata for fragment resolution. Every reference, and every inventory pointer, must land on a schema location: annotation data such as `examples`, `required` or an `enum` array, and a map or list of subschemas such as `properties` itself, is refused (`reference_to_non_schema`, or `invalid_inventory_pointer` for an inventory), and a referenced object must pass the metaschema itself (`invalid_referenced_schema`). The reference walk covers every subschema keyword, including `contentSchema`, legacy `dependencies` and `additionalItems`, so no keyword hides a remote reference. Example/default data is not interpreted as schema code. Unknown or unsupported finite-vocabulary constructions require an honest mapping gap instead of an exhaustive claim.

Input is bounded to 256 KiB (`input_size_limit`; the Python entry point measures the compact UTF-8 serialization, counting a lone surrogate at its six-byte escape), each artifact to 1 MiB (`artifact_size_limit`), the schema documents parsed in one run to 4 MiB in total (`schema_total_size_limit`, checked before another document is parsed), declaration lists to 256 items, schema graph depth to 128 (a `$ref` chain an inventory is projected through is bounded the same way, reported as `schema_depth_limit` at that inventory's pointer), the projection of one inventory to 10,000 uncached steps (paths that inherit different `required` names cannot share memoized work; past it, `projection_work_limit` at that inventory's pointer), rendered CLI output to 256 KiB (escaping can roughly double a permitted input; past it, the CLI prints a report carrying only `output_size_limit` instead of a truncated one) and schema strings to their published individual bounds. The CLI consumes JSON with duplicate-key/nonfinite-number rejection. The neutral tool `limits` fields describe the domain's host bounds, not limits imposed on that domain by this offline validator.

## Compatibility, release and ownership

[Codex baseline observations](../openspec/changes/archive/2026-10-06-add-factory-mcp-conformance/review/codex-baseline-2026-09-07.md) pin revision `4b12ba83add713666a94129fc45552d8989f8488` of `codeXfactory/codexFactory` and the digests of its three published schemas (tool request, tool result, domain error). This profile leaves those schemas, their outputs and client compatibility unchanged. The observation is a compatibility review input, not an executable codex declaration or adoption certificate. codexFactory is private, so this repository carries no codex schema bytes: a reviewer with access validates a codex declaration out of tree, supplying the codex snapshot with `--snapshot`.

A hosted engineering declaration made before the authorization block has none, so it reports `hosted_auth_missing` until the engineering domain's own slice declares one; a block that lists EdDSA alone reports `auth_rs256_missing`. That is the intended signal. Its stdio declaration is not deployed and validates as before.

DNS behavior remains in OpsxFactory, whose DNS check is callable-only with no hosted declaration. This repository ships synthetic domain fixtures only.

The profile is unbundled and unreleased. Register manifest/changelog digests, allocate the additive contract version and accept consumer pins only in the later governed realization. This work creates no listener, shared transport, release tag, accepted deployment or production endpoint.
