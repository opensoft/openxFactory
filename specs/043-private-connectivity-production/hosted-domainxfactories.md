# Hosted DomainxFactory production acceptance

Status: draft
Created: 2026-11-13
Feature: [043-private-connectivity-production](spec.md)

Each actual domain workload and exact hosted profile is qualified separately. The feature 040 codeXfactory lab profile does not select or approve a production domain.

### D-01: Qualify the actual workload and exact profile

The selected production domain owner supplies its actual workload, immutable exact profile/candidate, access declaration and lifecycle evidence. The profile stays ineligible if evidence names only a synthetic workload, another domain/profile or an unapproved environment. Its own current owner release acceptance is required.

### D-02: Protect and validate every production profile

An owner-approved strict schema and semantic checks reject unknown fields and invalid scope. Exact definition-time protection and mandatory validation wiring cover each production profile before qualification. Catalog eligibility derives from current exact-profile release authority and evidence. Caller-supplied eligibility, stale evidence, a mismatched domain/environment or another profile's results cannot grant customer eligibility.

### D-03: Onboard private managed-new and managed-existing profiles

Observe both actual onboarding paths with a service eligible for the same approved phase/scope, current entitlement and scoped attachment authority. Required private access and application authorization pass before readiness; private endpoints have no public ingress. Partial provisioning, policy, enrollment or application/connectivity failure reports the failed step without secrets, remains unready and reconciles the original operation without duplicate networks or exposure.

### D-04: Enforce application authorization after network access

A legitimately connected client without the application's required permission is denied. The successful control is a correctly authorized application client on the same qualified profile. Network membership or routing approval alone cannot establish application authority.

### D-05: Qualify an unbound domain without a forced network subscription

A profile with no private access requirement can qualify its own unbound deployment and application lifecycle without a private-network subscription. This is not permission to remove required privacy from a private profile. Removing a factory revokes its attachment and preserves independently entitled networks and unrelated authorized devices.

### D-06: Requalify affected profiles and bound every release

A successful domain canary qualifies only its approved exact scope. Another profile/domain remains ineligible until its own qualification and release decision exist. Material changes to artifacts, profile, provider, identity integration, region or policy trigger impact review, affected staging/canary reruns and renewed authority. Each commercial offer or expansion wave names exact eligible profiles, customer/region/resource bounds and accepted canary evidence.

## Qualification evidence

The domain owner supplies actual application/access/lifecycle evidence, exact profile protections and current approvals. The product owner supplies integration/onboarding/catalog evidence; the managing factory supplies target execution and operational acceptance. Q0 must select the production domain and its owner before domain-specific implementation. Q1–Q5 decisions cannot reuse the five historical lab-role approvals. See [commissioning](commissioning.md) and [rollout gates](rollout-gates.md).
