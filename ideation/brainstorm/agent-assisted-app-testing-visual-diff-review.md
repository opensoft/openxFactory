# Visual Diff Review — Brainstorm

Status: brainstorm
Kind: process
Summary: Keep the original deterministic screenshot comparison authoritative while generating dimension-preserving, normalized derivatives that help specialist agents, Subject Hermes, and optional human reviewers understand meaningful visual changes.
Topics: agent-assisted-app-testing, visual-diff, pixel-comparison, preprocessing, s-rgb, masking, review-evidence
Repository context: openxFactory; browser visual-review pipeline for Loki/Playwright captures with a later Flutter golden-test analogue

## Possible feats

- **Deterministic diff evidence packet** — preserve baseline, current capture, raw diff, metrics, masks, and render identities as immutable review inputs.
- **Reviewer derivative pipeline** — produce explainable overlays and focus views without changing the pixels used by the blocking comparison.

## Focus

Vision models and human reviewers benefit from a readable comparison image, but preprocessing can accidentally destroy the evidence it is meant to explain. A resized, histogram-equalized, or edge-only image may be useful for visual reasoning while being unsuitable as the authority for pixel approval.

The pipeline should therefore have two explicit products:

```text
raw captures ──► deterministic comparison ──► blocking/advisory metrics
       │
       └────────► reviewer-friendly derivatives ──► specialist/Hermes interpretation
```

The derivative is evidence about the raw comparison, not a replacement for it.

## Authoritative comparison rules

- **Preserve dimensions:** baseline and current images must have the same width, height, color encoding, and capture region. A dimension mismatch is a failure or an explicit recapture condition; resizing must not conceal geometry drift.
- **Standardize color carefully:** captures should be normalized to a documented sRGB policy before comparison, while the original files and color metadata remain available for audit. Do not use histogram equalization in the blocking path because it changes the color relationship being tested.
- **Keep exact pixels:** the raw baseline, current image, and generated diff must be retained with hashes and profile identity.
- **Use explicit masks:** dynamic regions such as timestamps, randomized IDs, or intentionally animated surfaces may be masked only by named, versioned masks. A mask should include its reason, owner, scope, and review history.
- **Measure more than a ratio:** record differing-pixel count and ratio, connected regions, bounding boxes, per-region metrics, and whether the change intersects the annotated target or a protected critical region.
- **Separate tolerance from acceptance:** thresholds are policy inputs for a named profile; a threshold change is itself a reviewed policy change, not a side effect of a baseline refresh.

The blocking result should be reproducible from the raw artifacts and the manifest. A vision model may explain the result, but it should not be required to reproduce the pixel arithmetic.

## Reviewer derivatives

Useful derivative views can include:

1. baseline and current images side by side at their original aspect ratio;
2. a raw or thresholded difference heatmap;
3. an alpha overlay showing movement and alignment;
4. crops around changed connected regions, with the full viewport retained as context;
5. optional edge or geometry views for layout questions;
6. accessibility-tree, DOM geometry, token, or semantic-role summaries when available.

Derivatives should declare their transform, input hashes, output dimensions, and intended use. A fixed model input size may be generated by letterboxing or by producing multiple tiles, but arbitrary stretching to `1024x1024` should not be used for geometry review.

Edge detection can help a reviewer see boundary shifts; it cannot establish that fills, typography, contrast, or color are correct. Likewise, contrast enhancement may improve a human's ability to find a subtle change but must never rewrite the source images used for approval.

## Review lanes

| Lane | Evidence | Decision role |
|---|---|---|
| Canonical visual gate | Raw Loki/Chromium capture, exact diff, profile threshold | Deterministic pass/fail or needs-review result |
| OS parity | Raw user/OS capture plus geometry/semantic comparison | Advisory or profile-specific acceptance, depending on policy |
| Specialist/authority review | Raw evidence plus declared derivatives and machine metrics | Explain, classify, support Experience Council findings, and propose next action |
| Baseline migration | Before/current/expected images plus manifest/profile lineage | Candidate update for explicit approval |

The same capture should not be silently interpreted under two different profile identities. If the viewport, state, or render manifest differs, the system should report that the comparison is not equivalent and route it to parity or recapture handling.

## Interfaces and boundaries

The diff service consumes immutable captures, approved baseline metadata, render manifests, fixture/state hashes, and mask definitions. It emits machine metrics, derivative artifacts, and a structured review packet.

It does not approve a new baseline, hide a failing region through an unreviewed mask, or infer that a platform difference is harmless solely from pixel similarity. It also does not substitute for functional, accessibility, workflow, Experience Council, or Project Owner assertions.

## Alternatives and tensions

- **Raw pixel diff only:** deterministic and auditable, but less useful for explaining why a difference matters.
- **Vision-only review:** flexible across rasterization differences, but probabilistic and difficult to audit as a blocking rule.
- **Aggressive preprocessing:** makes differences visually salient, but can remove the very color and geometry signals under review.
- **Region-level review:** focuses attention and reduces model input size, but can miss viewport-level layout shifts.
- **Strict no-mask policy:** maximizes coverage, but dynamic content can create unusable noise; masks need governance rather than informal exceptions.

## Open questions

- Which color-management and screenshot-output policy will all supported runners use?
- Which image-diff algorithm and thresholds are suitable for canonical gating versus advisory parity?
- How are masks authored, tested, expired, and prevented from covering protected targets?
- Should derivatives be stored in Git, as CI artifacts, or in a content-addressed review store?
- What evidence is sufficient for a Flutter golden-test adapter, where device and platform rendering may be even more variable?
