## 3.1 (a) — The harness's memory backends

**Method:** hands-on install + source read (`docs/memory.md`,
`docs/mnemosyne-memory-backend.md`, `packages/coding-agent/src/config/
settings-schema.ts`, `packages/coding-agent/src/memory-backend/resolve.ts`,
`packages/coding-agent/src/memory-backend/off-backend.ts`).

**Evidence:**
- Four backends exist, selected by a single enum setting:
  `packages/coding-agent/src/config/settings-schema.ts:2620-2640`:
  ```
  "memory.backend": { type: "enum", values: ["off","local","hindsight","mnemopi"], default: "off", ... }
  ```
- Selection is centralized in one function, `resolveMemoryBackend()`
  (`packages/coding-agent/src/memory-backend/resolve.ts`), whose own comment
  states: *"Selection rules (single source of truth — every memory consumer
  routes through this)"* — an if/else on `memory.backend`, falling through to
  `offBackend` for anything else.
- `off` is a true no-op (`packages/coding-agent/src/memory-backend/
  off-backend.ts`): every method (`start`, `buildDeveloperInstructions`,
  `clear`, `enqueue`) is empty; `status()` reports `active: false, writable:
  false, searchable: false`.
- What each backend stores, on disk, when selected:
  - `local`: `MEMORY.md`, `memory_summary.md`, `skills/*/SKILL.md`,
    `learned.md` under the agent's memories dir — generated by an LLM
    extraction/consolidation pipeline over past session JSONL, redacted for
    secrets before write.
  - `hindsight`: nothing local — a **remote** bank-scoped store reached over
    HTTP (`hindsight.apiUrl`, default `http://localhost:8888`); "does not
    delete the server-side bank" on `/memory clear`.
  - `mnemopi`: local SQLite, default path `<agent memories dir>/mnemopi/
    mnemopi.db`, with sibling per-project bank files under the same directory
    (`docs/mnemosyne-memory-backend.md` "Operational notes").
- Default is `off` for every install unless explicitly configured
  (`memory.backend` default `"off"`; also `providers.tinyModel`, `.memoryModel`,
  `.autoThinkingModel` default to `online`, i.e. no local inference happens
  unless opted into separately).

**FINDING:** Four mutually exclusive backends (`off | local | hindsight |
mnemopi`), gated by one enum setting resolved through one function that is
the acknowledged single source of truth. The off switch is not merely
present — it is the **default**, and disabling is a genuine no-op (empty
methods, not a suppressed-but-still-running backend). Mutual exclusivity is
structural (one enum value, not independent toggles), not merely
conventional.

**Implementation consequence:** design §5.2's split-brain prohibition
("Worker-Local Memory Remains Separate... the harness's native memory backends
never hold the threads") is enforceable as a **hard install-time
configuration fact**, not merely a documented policy the harness could quietly
violate: an install that ships with `memory.backend: off` (the shipped
default) has zero native memory surface for the bridge to accidentally leak
threads into. The realization (§11.5, task 11.5) should pin `memory.backend:
off` in the bridge's own launch config/profile explicitly (belt-and-braces
over relying on the operator never having opted in), since a
manually-configured `local`/`hindsight`/`mnemopi` backend on the *invoking
engineer's* general-purpose omp profile would otherwise still be live and
"ranked last" per design's own text — worth stating in the realization that
the bridge should launch under a **dedicated profile** (`--profile
<doxbench-bridge-name>`) precisely so a developer's personal interactive omp
memory settings can never bleed into the bridge's sessions.

> **ADDENDUM — 2026-08-19, live re-verification during §11's realization.**
> This finding records the SETTING (`memory.backend`, its enum, its default,
> its resolution function) but not how a launcher sets it, and the first
> realization guessed `--setting memory.backend=off`. **There is no such
> flag**: real v17.3.7 answers `Error: unknown flag: --setting` and exits, so
> that launch line could never start a harness. The real per-run mechanism is
> `--config=<value>` ("Load an extra config.yml-style overlay for this run",
> repeatable), whose precedence is
> `defaults <- global <- project <- PI_CONFIG_FILES <- --config <- runtime` —
> i.e. it outranks both the operator's global settings and the project's.
> The overlay is nested YAML and the value must be QUOTED, because bare `off`
> is a YAML 1.1 boolean while the setting is a string enum:
> ```yaml
> memory:
>   backend: "off"
> ```
> Verified observable from inside the running session: with this overlay
> `/memory diagnose` answers *"Memory backend is off — there is nothing to
> show."*, and with `backend: local` in the same slot it answers something
> else. So §11.5's "install fact, not policy" is now a fact the harness itself
> reports, rather than a claim about a flag it rejects.

This is a strengthening finding, not a blocking one — no design section needs to
reopen.

## 3.2 (b) — MCP client depth

**Method:** fully hands-on, end-to-end, real dispatch. Wrote a ~90-line
hand-rolled stdio MCP server (`echo-server.mjs`, implements `initialize`,
`tools/list`, `tools/call` per the MCP 2025-03-26 spec) exposing one tool,
`echo`. Registered it in a project-scoped `.omp/mcp.json` (`stdio` transport,
`command: node`). Started `omp --mode rpc` against the local mock model
described above, sent a single `prompt`, and inspected the full RPC event
stream.

**Evidence:**
- Discovery: `docs/mcp-config.md` documents three transports (`stdio`,
  `http`, `sse`), project + user + cross-tool config discovery
  (`.omp/mcp.json`, `~/.omp/agent/mcp.json`, plus imported Claude
  Code/Codex/Gemini/Cursor/Windsurf/VS Code configs), and `/mcp
  list|test|reconnect|reload` management commands.
- Dispatch mechanism, from `packages/coding-agent/src/tools/xdev.ts:1-30`
  (docstring, verbatim):
  ```
  Discoverable built-ins and custom tools are unmounted from the request's
  tools array and exposed as internal URLs driven through the read/write
  tools the model already has:
    read  xd://          → mounted tool listing (discovery)
    read  xd://<tool>    → tool docs + JSON parameter schema
    write xd://<tool>    → execute: `content` is the JSON args object
  ```
  MCP tools beyond a small always-top-level built-in set (`read, bash, edit,
  eval, glob, grep, task, hub, todo, web_search, write` in our run) are
  **not** separate native function-calling schema entries; they are mounted
  as `xd://` "devices" whose full docs + JSON schema are inlined into the
  system prompt, and invoked by the model issuing an ordinary `write` tool
  call whose `path` is `xd://<mounted-name>` and whose `content` is the JSON
  argument object.
- Live proof: our custom server's tool appeared in the running system prompt
  as `xd://mcp__verify_echo_echo` (alongside other ambient MCP servers this
  host had configured, e.g. `xd://mcp__sonarqube_*`, confirming the discovery
  layering is real and not special-cased for our test server).
- Full round trip, captured from the RPC stdout stream:
  ```
  "type":"tool_execution_start","toolCallId":"call_1","toolName":"write",
  "args":{"path":"xd://mcp__verify_echo_echo","content":"{\"text\":\"hello-check\"}"}
  ...
  "type":"tool_execution_end" ...
  ```
  and the echo server's actual reply text, `ECHOED:hello-check`, appearing in
  the subsequent `message_update` deltas fed back to the (mock) model, which
  then produced its final assistant turn and a terminal `agent_end`.

**FINDING:** OMP is a genuine MCP **client** with real mid-turn tool-calling,
verified end-to-end (discovery → connect → schema-inline → model-issued call
→ real subprocess dispatch → result → next turn). The calling convention is
indirect (`write` to an `xd://` virtual path, JSON args as file content)
rather than one native function-schema entry per MCP tool — this is a
deliberate design choice in OMP to avoid per-tool schema duplication and to
control system-prompt size when many MCP servers are mounted, not a
limitation on reachability.

**Implementation consequence:** design §10.6/§3.3 assumed "the MCP boundary
is only reachable from the model if the harness can call tools at all" —
**confirmed reachable**. The knowledge service's four MCP tools (`search,
get_source, promote_finding, reindex`) will be dispatched by the model via
`write xd://mcp__<server>__<tool>` (exact mount name depends on the server
name chosen for the knowledge-service's own MCP registration — the
realization should pin and test the resulting `xd://` name string, since it
is derived from the server+tool name, not the bare tool name the contract
declares). §10's packet assembler is genuinely model-reachable, not merely a
server-side-only assembler. No design section needs to reopen; this
*validates* the existing plan rather than changing it, with one concrete
realization note: the bridge/adapter (§5) must ensure the knowledge-service
MCP server is registered before the first turn of a document thread that
needs it (MCP discovery is documented as asynchronous — see the "RPC
mechanics" note below — so a turn issued before discovery completes will
simply not see the tool that turn, degrading exactly to design §3.4's
"no knowledge service" reduced-packet posture, which is the correct fallback
already specified).

## 3.3 (c) — `SYSTEM.md` re-read cadence

**Method:** source-level trace of the exact call path from CLI argument
parsing to system-prompt rebuild (`packages/coding-agent/src/main.ts`,
`packages/coding-agent/src/sdk.ts`, `packages/coding-agent/src/session/
session-tools.ts`), cross-checked against `docs/system-prompt-
customization.md`.

**Evidence:**
- `main.ts:924`: `const systemPromptSource = parsed.systemPrompt ??
  discoverSystemPromptFile();` — discovery happens once, during CLI startup,
  before session creation.
- `main.ts:891`: `options.customSystemPrompt = resolvedSystemPrompt;` — the
  resolved text is written once into the `CreateAgentSessionOptions` object
  that is closed over for the life of the process.
- `sdk.ts:2812` defines `rebuildSystemPrompt`, the callback invoked whenever
  the system prompt needs rebuilding (tool-registry changes, model changes,
  vision-mode toggles — see `session-tools.ts:1326-1339`,
  `refreshBaseSystemPrompt()`, doc comment *"Rebuilds the **stable base
  prompt** for the current tools and model"*, triggered by
  `runToolRegistryMutation`, i.e. tool/model events, not a timer or a
  per-turn hook).
- `sdk.ts:2902`, inside that same rebuild closure: `resolvedCustomPrompt:
  options.customSystemPrompt` — every rebuild, however triggered, reuses the
  **same string captured once at startup**. There is no call to
  `discoverSystemPromptFile()` or any disk read of `SYSTEM.md` inside the
  rebuild path.
- Corroborating design rationale from `docs/system-prompt-customization.md`:
  the current date/cwd were deliberately **moved out** of the system prompt
  into a per-turn `<system-reminder>` block specifically *"to let a session
  crossing midnight refresh the date without rebuilding the prompt"* — i.e.
  the authors treat "rebuilding the system prompt" as an event to avoid on a
  hot path, which only makes sense if the prompt (including the `SYSTEM.md`
  contribution) is otherwise stable for the session.

**FINDING:** `SYSTEM.md`/`APPEND_SYSTEM.md` are read from disk **once, at
process/session startup**, not per turn. Rebuilds do happen mid-session (on
tool/model-registry changes) but always replay the same startup-captured
string — a change to `SYSTEM.md` on disk after a session starts has zero
effect on that running session, regardless of how many rebuilds occur later.

**Implementation consequence:** design §10's source-ranking hierarchy
(`SYSTEM_CONTRACT_TEXT`) is fixed for the life of a bridge-managed harness
session, exactly as design assumed. Confirms the consequence design already
drew: **a hierarchy change requires a session restart** (i.e. a new harness
session, which per §5.2 the bridge already creates on demand per document
thread — so the realization gets this for free as long as the bridge always
starts a **fresh** harness session per thread rather than reusing one across
a system-prompt-relevant settings change). No design section needs to
reopen; task 5.5 (`SYSTEM_CONTRACT_TEXT`) can proceed as specified.

## 3.5 (e) — Where the harness's session artifact store lands on disk

**Method:** source read (`docs/session.md`, `docs/blob-artifact-
architecture.md`) plus hands-on confirmation: a real persisted session was
created via `omp --mode rpc --session-dir <scratch>` and its `sessionFile`
path inspected via `get_state`.

**Evidence:**
- `docs/session.md`, "On-Disk Layout": *default* file-session location is
  ```
  ~/.omp/agent/sessions/<encoded-cwd>/<timestamp>_<sessionId>.jsonl
  ```
  — under the harness's **own home-directory config tree**, keyed by an
  encoding of the process's cwd, not under the project/git worktree at all.
- `docs/blob-artifact-architecture.md`: `ArtifactManager` derives the
  artifact directory **from the session file path**: *"session file:
  `.../<timestamp>_<sessionId>.jsonl`; artifacts directory:
  `.../<timestamp>_<sessionId>/`"* — i.e. a sibling directory of wherever the
  session file lives. There is no independent artifact-directory
  configuration; it rides the session file's location exactly.
- Hands-on: our test session (`omp --mode rpc --session-dir
  $SCRATCH/omp-sessions-test ...`) produced `get_state.sessionFile` =
  `$SCRATCH/omp-sessions-test/2026-08-18T19-12-43-504Z_<id>.jsonl` — i.e.
  wherever `--session-dir` (or the default `~/.omp/agent/sessions/...`)
  points, full stop; nothing ties it to the invoking cwd's git structure
  beyond the cwd-encoding used to *name* the default bucket.
- `--session-dir` is a real CLI override (`omp --help`: *"Directory for
  session storage and lookup"*), so a caller **could** point it inside a git
  worktree, but that is not the default and nothing in the shipped harness
  does it automatically.

**FINDING:** The harness's own session/artifact store lands **outside** the
project's git worktree by default — in the harness's home-relative config
tree (`~/.omp/agent/sessions/...` unless `--session-dir` overrides it), keyed
to an encoding of the invoking cwd, with **zero relationship to git branches
or worktrees**. Nothing in the shipped harness makes `artifact://` content
"ride the branch" automatically.

**Implementation consequence:** this directly affects design §9 (threads)
and §12 (share-session), exactly as tasks.md's own framing anticipated.
Concretely:
- Phase B's thread **sidecar files** (design §4.1) are *not* the harness's
  native session/artifact storage — they are Phase B's own file writes,
  which the realization already commits into the actual git worktree (design
  §9.1: "on the session branch, inside the session worktree"). That part of
  the design is unaffected and correct as written: it does not rely on the
  harness's artifact store at all.
- The risk is narrower and specific: if the turn-mirroring step (§5.2 "the
  sidecar is the record... doxBench mirrors each turn into the sidecar")
  ever persists a **bare `artifact://<id>` reference** into a thread's
  transcript or evidence-refs (e.g. because a tool result was large enough to
  spill to the harness's own artifact store rather than being inlined), that
  reference is scoped to the originating harness session's home-relative
  directory and will **not** resolve for a colleague who fetches the shared
  branch via share-session's `push` (design §4.3) — the referenced file
  simply will not exist in their checkout, ever, regardless of what they
  fetch. **Task 9.1's realization should state explicitly that turn-mirroring
  into the sidecar dereferences (inlines) any `artifact://` content rather
  than persisting the pointer**, or, if inlining is infeasible for very large
  spilled output, that the sidecar records the *fact* that content was
  elided rather than an unresolvable pointer. This is a concrete addition to
  task 9.1/9.3's acceptance criteria, not a reopening of the design's
  architecture — the chosen architecture (Phase B writes its own sidecars)
  already sidesteps the general problem; this is the one leak point worth
  closing explicitly.

## 3.6 (f) — `/shake`'s trigger surface

**Method:** source read (`docs/compaction.md`,
`packages/coding-agent/src/slash-commands/builtin-lifecycle.ts`) plus
hands-on: sent `{"type":"prompt","message":"/shake elide"}` over a live `omp
--mode rpc` session (against the local mock model) and inspected the
response.

**Evidence:**
- `docs/compaction.md`: **both** surfaces exist.
  - Automatic: `compaction.strategy: "shake"` is a configurable auto-
    compaction strategy — *"Automatic shake emits the normal auto-compaction
    events with `action: "shake"`"* — plus a separate **idle-shake** timer
    path.
  - Manual: *"Manual `/shake` is a separate, more aggressive command that can
    target all eligible history."*
- Source (`builtin-lifecycle.ts:169-195`): `/shake` is registered as an
  ordinary builtin slash command with a generic `handle(command, runtime)`
  callback (`await runtime.session.shake(mode)`) used by every non-TUI host
  (RPC, ACP, print mode); `handleTui` is a **separate**, TUI-only handler.
  The generic path is not gated to interactive terminals.
- Hands-on, RPC stdout:
  ```
  {"id":"sh1","type":"response","command":"prompt","success":true,"data":{"agentInvoked":false}}
  {"type":"command_output","text":"Nothing to shake."}
  ```
  — executed with **zero model calls** (`agentInvoked: false`), confirming
  it is a local, deterministic, programmatically-reachable operation in
  `--mode rpc`, dispatched exactly as any other slash command: a `prompt`
  command whose `message` is the slash-command text.

**FINDING:** `/shake` exists as **both** a manual command and (via
`compaction.strategy: "shake"` plus idle-shake) an automatic mechanism, and
the manual command **is** reachable programmatically in `--mode rpc` — there
is no TUI-only gate. The exact command surface is:
```json
{"id": "<any>", "type": "prompt", "message": "/shake elide"}
```
(or `"/shake images"`), which returns immediately with
`data.agentInvoked: false` and a `command_output` frame carrying the shake
summary text — no distinct RPC command type exists for it; it rides the same
generic slash-command-over-`prompt` channel as `/mcp list` and every other
builtin command.

**Implementation consequence:** design §5.1/§8 ("`/shake`-style offload is
inside the adapter") and compression layer 3's realization are **not**
blocked — the mechanism a server can rely on is confirmed to exist and is
exactly the `prompt`-with-slash-text shape above. The realization (§10, the
compression stack) should route layer-3 shake invocations through this exact
JSONL shape from the bridge, and should parse `command_output.text` (a
free-text summary, not a structured payload) for its own bookkeeping/logging
— there is no structured "bytes reclaimed" field in the RPC response beyond
that text, which is a minor precision the realization should not assume
otherwise.
