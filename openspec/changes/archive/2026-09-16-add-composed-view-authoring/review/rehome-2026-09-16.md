## NO DELTA IS PROMOTED, AND THAT IS THE PACKET'S INSTRUCTION

The one `## MODIFIED` block is **not** applied to
`openspec/specs/ideation-dashboard/spec.md`. The packet says so twice — once as
the general rule for the five, *"their `## ADDED` blocks never promote HERE and
their content is re-authored in the receiving repository"*, and once in the
migration voice of this requirement's own successor row, *"the requirement is
re-promoted in `opensoft/openDox`'s own OpenSpec instance"*.

This is why the relocation is a `git mv` rather than the governed archive
route — and the reason is both stronger and narrower than *"the archive commands
always promote"*, which an earlier draft of this record said and which is not
true of the pinned CLI.

**THE GOVERNED WRAPPER REFUSES THIS PACKET OUTRIGHT, BEFORE PROMOTION IS EVEN
REACHED.** `archive_change` raises `change has incomplete tasks` for any packet
whose `tasks.md` still carries a `- [ ]` line, and it raises it before the
pinned CLI is resolved at all. RULING Q6 freezes all five WHERE THEY STAND, so
every one of the five arrives at its closure with open boxes — this one with
§ 3.2 — and `scripts/proposal-support.py … archive` is therefore not a sanctioned
route that would promote too much here: it is a sanctioned route that does not
run at all.

**AND IF IT RAN IT WOULD PROMOTE**, because it exposes no way not to:
`proposal-support.py … archive --help` lists `--date`,
`--final-import-complete`, `--yes` and `--path-mode`, and nothing else.

**THE PINNED CLI UNDERNEATH IT IS DIFFERENT, AND THE DIFFERENCE IS RECORDED
RATHER THAN BLURRED.** `openspec archive` at the pinned `1.12.0` DOES take
`--skip-specs` — *"Skip spec update operations (useful for infrastructure,
tooling, or doc-only changes)"* — measured by running the pinned artifact's own
`archive --help`, and the wrapper's own docstring enumerates that same flag set
(`scripts/proposal-support.py:4133-4135`). So a non-promoting archive mode
EXISTS; it is simply not reachable through the governed path. Reaching it means
running the CLI around the wrapper, which is the move that wrapper's own comment
records as the failure it was extended to prevent (*"pushed the operator toward a
bare `openspec archive` and around this gate entirely"*), for a ratified
capability delta that is none of the three things the flag's own help describes.
A wrapper run followed by a hand-revert of the promotion hunk would have produced
the same tree through an act whose record said the opposite. The `git mv` is the
act this record can state without qualification, and the one a reviewer reads for
what it is: a rename.

**WHAT THE WRAPPER GUARDS IS SATISFIED BY HAND AND CHECKED, NOT WAIVED.** This
packet DOES carry a `.openspec.yaml`, and it carries an `origin:` declaration
inside it (`kind: ad_hoc`,
`id: openxFactory:adhoc:2026-08-08-add-composed-view-authoring`, swept in by the
2026-08-25 ruling) — an earlier draft of this record said the opposite and was
wrong. That file is precisely what `origin_errors` and `origin_retention_errors`
read at the wrapper's gate, and the rename carries it byte-for-byte: the diff
shows `.openspec.yaml` as a pure rename with no content hunk, so the declaration
this closure retains IS the declaration the ORIGIN RETENTION gate would have
compared, and the retention is checkable on the diff rather than asserted here.
The archive directory name is the one the wrapper would have computed —
`<today in UTC>-<id>`, the id carrying no date prefix of its own.
