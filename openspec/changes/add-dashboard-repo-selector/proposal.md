# Proposal: add-dashboard-repo-selector

## Why

The dashboard shows ONE repository — openxFactory — and it shows the copy
of that repository's corpus that happened to be baked into the container
image. Both halves of that sentence are now costing real work, and Brett
decided both of them the same week.

FIRST, the family has nine repositories and the dashboard can see one of
them. A live drive on 2026-07-25 ran the UNMODIFIED v1 generator against
MedxFactory (31 documents / 1 change), AdxFactory (7 / 1), and
LedgerxFactory (9 / 3) with ZERO code changes — the generator, the
snapshot schema, and the wheel rendering are already repository-agnostic.
What is missing is not neutrality; it is a selector, a snapshot per
repository, and a thin index for the selector to read. The
project-register contract that would be that selector's roster already
exists (neutral schema in openxFactory, instance owned by the aggregation
layer), and the generator already resolves a repository through it. This
is the dev-plane step toward the decided end state — the dashboard as a
neutral capability every DomainxFactory install ships — with the two
planes kept as separate systems: a dev dashboard never reaches a running
install's content.

SECOND, and this is the part that bit someone: the snapshot is baked into
the image, so the dashboard's data can only change when the image changes.
On 2026-07-25 at ~20:30 UTC a new staging fragment landed on openxFactory
main (`ab2acad`) MINUTES after that day's rebake. It was invisible on
ideation-dashboard.xforge.us until the nightly ran AND the image was
rebaked — and invisible on the local serve until someone regenerated by
hand. The user question behind the complaint is small and reasonable:
"did my doc make it in?" Today answering it requires knowing when an image
was built. Brett's ruling (2026-07-25, relayed via team003, endorsing
team003's option 2) is to fix it INSIDE this change rather than bolt a
bake trigger onto the pod: **bake the APP, not the SNAPSHOT.** The pod
fetches its data at runtime; a refresh button re-fetches; the baked
snapshot survives only as a first-boot and offline fallback that says so.

THIRD, the two halves are the same seam. Per-repository snapshots plus a
thin index is exactly the shape the selector needs, and moving where those
files are READ FROM is most of the decoupling. So one seam serves both —
and Brett keyed it (2026-07-26) on the PAIR **(repository, ref)** with
`ref` defaulting to `main`. The hosted plane will only ever exercise
`(repo, main)`, but carrying `ref` from day one is what lets the branch
sessions of the sibling staged topic
(`ideation/staging/workbench-branch-sessions/`) and the eventual runtime
plane bind to this interface instead of forcing it to be re-cut. Adding a
second key later would mean re-cutting the ONE interface every renderer,
the index, and both refresh bindings pass through.

## What Changes

- ADD a REPOSITORY SELECTOR over the repositories the project register
  declares. The register is the roster — no second repository list is
  invented, and no repository must adopt any convention to be selectable.
  A repository renders whatever funnel stations it has data for; an
  install repo carrying only `openspec/changes/` renders active and
  archived and nothing else. Sparse wheels are honest wheels.
- KEY the snapshot source on the PAIR (repository, ref), with `ref`
  defaulting to `main`, and give the serve ONE registry keyed by that
  pair. This is the change's load-bearing seam: the selector reads it, the
  index describes it, both refresh bindings drive it, branch sessions will
  consume it, and the runtime plane will bind its own source behind it.
  Snapshots for a ref other than `main` are session-local derived data and
  are NEVER published.
- ADD a thin SNAPSHOT INDEX artifact — one entry per available
  (repository, ref) with its location, `source_revision`, and generated-at
  — carried by its OWN new schema rather than grown into the snapshot
  schema (design D3). The index is what the selector renders and what a
  refresh re-fetches; it carries no funnel data.
- BAKE THE APP, NOT THE SNAPSHOT. The served image carries the renderer
  and its assets; the index and the active snapshot are fetched at RUNTIME
  from a declared external data source by the SERVING SIDE, into a
  same-origin snapshot directory the bundle already knows how to read
  (design D5 — the bundle's no-external-URL boundary is grep-proven and
  stays that way). The recommended source is the aggregation repo's
  `health/ideation-dashboard/` raw files — the nightly already writes
  exactly there, so no new publication path is invented, and provenance is
  trivially auditable because the fetched file's commit SHA IS the
  `source_revision` the snapshot already carries (design D2; the
  blob-container and ConfigMap alternatives, and the read-credential
  consequence that is the strongest argument against raw files, are
  recorded there, and ratification is open question 1).
- DEMOTE the baked snapshot to a FIRST-BOOT and OFFLINE fallback. When
  the fallback is what renders, a stale banner says so and names its
  generated-at. The one thing it may never do is degrade silently: a
  dashboard quietly serving last week's governance state is the failure
  this change exists to end.
- DISPLAY freshness in the header — `repo @ ref · source_revision short
  SHA · generated-at` — so "did my doc make it in?" is answered at a
  glance rather than by reasoning about deployment times.
- ADD one refresh affordance with TWO plane bindings. Hosted: re-fetch the
  index plus the active snapshot and re-render — strictly read-only, no
  new authority, because fetching fresh derived data is a read. Local
  serve: a POST route that re-runs the generator against the served
  checkout and re-renders, writing only the derived snapshot and mutating
  no governed content (gated versus ungated is open question 3;
  recommendation: ungated like `open-workbench`, because the artifact is
  derived).
- MAKE the nightly snapshot job DISPATCHABLE (`workflow_dispatch`) so an
  off-cycle publication is a governed CI action a human or a session
  triggers. The pod gains NO build or rollout authority — surfaces
  dispatch recorded requests and never execute final actions, and a
  "commission a rebake" verb, if ever wanted, is a separate change at its
  own gate.
- FIX the `serve.py` relative-import quirk that forces POST routes to be
  reached through module invocation (`python3 -m ideation_dashboard.serve`)
  today. This change adds a POST route and two fetch paths; carrying the
  workaround into them is how a workaround becomes a contract.

## Impact

- Affected specs: `ideation-dashboard` — SIX ADDED requirements (the
  repository selector; the (repository, ref) snapshot source; the snapshot
  index contract; runtime data fetch with the baked fallback, its stale
  banner and the freshness header; the two refresh bindings; dispatchable
  publication that the served surface can never trigger) and TWO MODIFIED
  requirements (`Snapshot projection contract`, whose "v1 covers
  openxFactory only" clause and single-snapshot framing this change
  supersedes; `Delivery and regeneration`, whose "static renderer ...
  reading the adjacent snapshot" delivery model is exactly what the
  app/data split replaces). The `Project grouping hierarchy` requirement
  is NOT modified: it already declares the register as the neutral
  repository roster resolved into snapshot fields, and this change reads
  that roster rather than changing it. The `Interactivity boundary` is NOT
  modified either — a read-only re-fetch and a derived-artifact
  regeneration grant no authority the boundary withholds.
- Affected schemas: a NEW `ideation-dashboard-snapshot-index` schema plus
  packaged valid and negative examples, registered in
  `scripts/validate-ideation-dashboard-contracts.py`'s schema list and
  kind map. The `ideation-dashboard-snapshot` schema is NOT grown: the
  index describes a SET of snapshots and the snapshot describes one
  repository's corpus, so folding one into the other would make every
  snapshot carry facts about its siblings (design D3). No
  `contract_schema_version` bump anywhere; every existing snapshot stays
  valid, because a snapshot that names no ref is a `main` snapshot by the
  default (design D4).
- Delta stacking: the `ideation-dashboard` capability is NOT promoted
  (`add-ideation-dashboard` sits unarchived), so this delta stacks on it
  alongside `add-propose-verb`, `add-wheel-action-verbs`,
  `add-staging-workbench`, `add-lens-gate-verbs`, and
  `add-workbench-bullseye-and-create`.
- Archive sequencing: `add-ideation-dashboard` MUST archive BEFORE this
  change, because both requirements this change MODIFIES are requirements
  that change ADDS. Archiving in the other order leaves a MODIFIED delta
  with nothing to modify.
- Successor sequencing: `add-workbench-branch-sessions` (staged topic
  `workbench-branch-sessions`, decided 2026-07-26) CONSUMES the
  (repository, ref) seam and the snapshot registry this change lands, and
  is strictly sequenced after it. The seam is deliberately keyed for that
  consumer now rather than re-cut for it later.
- Affected code (codexFactory, realization): the snapshot generator's
  per-repository iteration over the register; a snapshot registry keyed
  (repository, ref) in `serve.py` with multi-root source confinement; the
  selector UI and the freshness header in the renderer bundle; a runtime
  fetch path for the index and the active snapshot with the baked-snapshot
  fallback and stale banner; the hosted refresh and the local regenerate
  POST route; the relative-import fix. The renderer bundle's pinned
  invariants apply and are why the fetch is POD-SIDE (design D5):
  `tests/ideation-dashboard/test_renderer.py` bans `https?://` and every
  network primitive across the whole bundle and pins each `fetch(` to one
  of a small set of same-origin backend routes. The browser therefore
  keeps talking only to its own origin; the DATA SOURCE is read by the
  serving side into a same-origin snapshot directory, so the grep-proven
  no-external-URL boundary survives this change unedited.
- Affected wiring (xFactory aggregation): the project-register instance
  grows the repositories to be offered; the published data source's layout
  is declared; the nightly snapshot workflow gains `workflow_dispatch`.
- NOT in scope: the runtime plane (the install-shipped neutral capability
  and its governed-content adapter — exit 2 of the staged topic, gated on
  what an "idea" IS as governed install content); the
  one-neutral-versus-per-domain-overrides fork, deliberately held open
  until domain driving yields vocabulary evidence; any pod-side build,
  rollout, or "commission a rebake" authority; branch/session snapshots
  and the workbench branch sessions that will consume this seam; the
  aggregate `xFactory` view's rendering shape beyond requiring that it
  compose from the index and never scan a repository (staged open
  question 1).
- Compatibility: additive throughout. An existing consumer that requests a
  snapshot without naming a ref gets the `main` snapshot; an existing
  published snapshot needs no rewrite; the index is a NEW artifact, so
  nothing reads it until the selector does. The served image keeps a baked
  snapshot, so a data source that is unreachable on first boot degrades to
  exactly today's behaviour — plus a banner that admits it.
