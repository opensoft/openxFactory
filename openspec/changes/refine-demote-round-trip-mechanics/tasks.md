Four parts, ordered so each is independently reviewable. Parts 1 and 4 both touch
the snapshot→plan path and are adjacent on purpose.

## 1. Origin resolution

- [x] 1.1 `generator._change_entry` resolves `origin_staging_id` from the change's
      own `.openspec.yaml` origin block where it declares `kind: staged`, falling
      back to the existing pick-edge mapping. Reuse `_load_openspec_meta`, which
      already parses that file for `_ratifier_of` — this part adds a reader, not a
      file read.
- [x] 1.2 The topic id comes from `origin.path`'s BASENAME, not from the namespaced
      `origin.id`. The field is compared against `staged_topics[].staging_id`, which
      is the bare topic; parsing the namespaced id would put the id's shape in a
      second place.
- [x] 1.3 A non-staged origin (`ad_hoc`, or absent) resolves NOTHING. The refusal
      stays, and its message keeps naming `--staging-topic`. Expect this to help 4
      of the 12 active changes; the other 8 have no topic to return to and asking is
      correct.
- [x] 1.4 Explicit `--staging-topic` still wins over both sources — it is already
      first in `plan_demotion`, so this is a test obligation rather than a code one.
- [x] 1.5 **PREMISE WRONG, corrected by measurement rather than left ticked.** The
      task predicted snapshot determinism pins moving for four changes. Measured at
      `8426dbc`: NO existing pin reads `origin_staging_id` — no test asserts it
      against the real corpus, and the base-repo fixture change carries no
      `.openspec.yaml`, so its pin still resolves through the retained pick-edge
      fallback and does not move. Nothing was regenerated and nothing was accepted.
      What the field really does is 35 changes gaining a value (4 active, 31
      archived) and 16 new `staged -> change` wheel edges rendering where 0 did;
      that is asserted in the proposal's Impact and covered by
      `test_the_recorded_origin_outranks_a_disagreeing_pick_edge` and its
      neighbours. The ONE pin that moved belongs to part 4:
      `test_a_demote_restores_an_absent_outline_and_refreshes_it`'s re-derived
      provenance dict.
- [x] 1.6 `origin.path`'s topic is the FIRST SEGMENT below `ideation/staging/`, not
      the path's basename. The forward gate accepts any directory below the staging
      root as its source, so a declared `ideation/staging/<topic>/openspec` resolved
      to `openspec` — a folder nobody named, into which the demote would then plan
      every returning file. A path outside the staging root resolves nothing.

## 2. The INDEX landmine — and the returned artifacts beside it

- [x] 2.1 The demote's `<topic>/openspec/INDEX.md` carries `Status: draft` — the
      state it shares with the returned drafts it lists, and regenerated by the next
      demote rather than durable evidence (design Decision 2).
- [x] 2.2 Driven, not asserted: demote a topic, then run the REAL forward transition
      over the whole folder and watch it not refuse. The defect was found that way
      and the fix does not get to be believed on less.
- [x] 2.3 **THE RETURNED-ARTIFACT HALF** (Brett's ruling, 2026-08-19, in-session
      multiple choice, recommended option adopted). 2.1 names only the first offender
      in sorted order: the forward gate refuses on the FIRST governed markdown
      without a header and `INDEX.md` sorts before `tasks.md`, which hid the rest.
      Measured at `8426dbc`: 93 of 94 `tasks.md`, 154 of 158 spec deltas, 65 of 68
      `design.md` and 49 of 94 `proposal.md` carry none. The demote's move arm adds
      `Status: draft` to any returned governed markdown lacking a header, through the
      status flip's own decode arm, preserving the document's line-ending flavor.
      2.2's driven test runs on that real shape rather than a tidied one. The
      byte-exact-move reading that deferred this was rejected as citing no ratified
      text; `test_a_crlf_document_survives_a_demote_move_byte_exactly` was a
      wave-re-review regression pin and is updated to the new contract.
- [x] 2.4 **THE OUTLINE'S REFRESH-IN-PLACE ARM**, which 2.3 wrongly declared out of
      scope. The claim was that the outline's source always arrives carrying a
      header; that holds for the SNAPSHOT the restore arm applies and fails for the
      LIVE FRAGMENT the refresh-in-place arm reads — a document the human owns,
      which never passed the forward gate. Demonstrated: a header-less working
      outline demoted cleanly (`outline_refusal: None`) and left the topic one-way.
      The refreshed bytes now go through the same add, with the value `staged`
      (the ratified primary-fragment rule, taken from the same expression the
      restore arm uses — NOT the `draft` returned change artifacts get). The add
      defers to an existing header, so a live fragment's own status is still never
      rewritten. The preserved-snapshot copy the same arm writes gets the same
      treatment at `draft`.
- [x] 2.5 **ONE STATUS GRAMMAR ACROSS BOTH GATES.** `gate_console._status_row`
      (15-row window, fence-blind, prefix match) disagreed with
      `proposal-support._status_row` (whole document, fence-aware, strict) on 11 of
      the corpus's 1133 markdown documents — 10 of them documents the forward gate
      REFUSES but the demote judged headed (7 archived-change evidence artifacts
      with `Status: record · …` / `Status: record (in progress — …)`), and a real
      header below row 15 that was invisible here, so a SECOND one was inserted
      beside it. Aligned; the two now disagree on 0 of 1133, and they are pinned
      against each other in the same file as the fence-flag agreement test. The
      strict grammar also stops `_flip_status` overwriting such a line, which was
      silent data loss dressed as a status flip.

## 3. The `Proposed by:` line

- [x] 3.1 `proposal_support.proposed_content` UPDATES an existing authorship line
      instead of adding a second.
- [x] 3.2 The demote's bounded refresh is NOT touched. Deduping there would widen
      the boundary the promoted requirement pins as "leaving every other byte of that
      file unchanged", trading a data-loss guarantee for tidiness (design Decision 3).
      Assert the boundary still holds after this part. NOTE the one carve-out 2.4
      adds to that same byte bound, so the two texts do not disagree: a lifecycle
      status header added where the fragment carries NONE, named in the execution
      record. An authorship dedupe is still not one of those — that bound admits
      exactly one addition, and it is the one without which the topic cannot be
      transitioned at all.
- [x] 3.3 The record is FENCE-AWARE and ANCHORED to the status header's own block.
      A `Proposed by:` inside a ``` block is an example: reading it as the record
      both suppressed adding the real one (against this change's own ADDED scenario
      "the record MUST be added") and rewrote somebody's example to name the current
      change. A record far below the header is not this document's record either —
      rewriting it there left the header block with none and relocated a governance
      line into prose.
- [x] 3.4 Pre-existing DUPLICATES are collapsed to exactly one. The ratified
      requirement is unconditional ("the document MUST carry exactly one such
      record"), and refreshing one of three while leaving two stale satisfies the
      letter of an update and none of the point. Outside fences only, and the
      collapse reaches the WHOLE DOCUMENT rather than only the header block — only
      the KEPT record is anchored there. Stated in the delta and the docstring
      because it is a scope a reader would otherwise have to infer from code;
      measured at 0 of 1133 corpus documents at risk today.
- [x] 3.5 The status flip stops eating bytes it never owned. `^Status:\s*staged\s*$`
      consumes the newline after the header (`\s*` is greedy, `$` is satisfied one
      line later), so a human's blank line between the header block and the body was
      deleted on every lap — seven lines in, six out. `\s*`/`.*$` also swallow a
      `\r`, so the rewritten line came out LF in a CRLF document. Both gone: the
      rewrite is row-based and each line keeps the ending it had.

## 4. The state-at-demote slot (Brett's Decision 3)

- [x] 4.1 `DemotionPlan` carries the change's `task_progress` beside
      `status_at_demote`, from the snapshot — same reasoning as the status before it:
      the plan is snapshot-derived and the executor never sees a snapshot.
- [x] 4.2 The slot renders `active — 9 of 22 tasks done`; plain prose, because the
      other four slots are prose and a human reads them in a markdown document.
- [x] 4.3 Absent progress renders the status ALONE, not `active — unavailable`. The
      promoted unavailable rule is about a value that could not be RESOLVED; a change
      with no tasks has none to resolve, and reporting a lookup failure where there
      was none would be a different lie.
- [x] 4.4 A progress record that does not add up (`completed > total`, or negative)
      renders the status alone as well. Unreachable through the generator, which
      counts both out of one sweep — guarded anyway, because the slot is prose a
      human reads as fact and `9 of 4 tasks done` is a fabricated one.
