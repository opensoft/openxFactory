# Design: refine-demote-round-trip-mechanics

Status: draft

Four parts, three owners, and the reason they are one change: all four are defects
or gaps in the same round trip, found on the same lap, and splitting them would
mean three changes each too small to carry its own reasoning.

## Decision 1 — origin resolution lands in the GENERATOR, not only the planner

`plan_demotion` reads `change["origin_staging_id"]` from the snapshot. The snapshot
is built by `generator._change_entry`, which currently derives that field only from
the pick-edge mapping `_derive_counts` assembles. So the honest fix is at the
source: `_change_entry` resolves the field, and `plan_demotion` keeps reading it.

`_load_openspec_meta` already exists in `generator.py` and already parses the
change's `.openspec.yaml` — it is called by `_ratifier_of` and nothing else, and the
`origin` key it loads is read nowhere. So this part adds a reader for data the
generator is already holding, which is why it is small.

**The topic id comes from `origin.path`'s basename**, not from `origin.id`. The
declared id is namespaced (`openxFactory:staging:<topic>`) while the field this
populates is compared against `staged_topics[].staging_id`, which is the bare topic.
Deriving from the path keeps one spelling; parsing the namespaced id would introduce
a second place that knows the id's shape.

**Only `kind: staged` yields a topic.** An `ad_hoc` origin means the change did not
come from staging, so there is nothing to resolve and the refusal is correct. This
is why the fix helps 4 of 12 changes rather than 12 of 12, and the proposal says so
rather than implying a total cure.

Rejected: making `plan_demotion` read `.openspec.yaml` itself. It is pure and
snapshot-derived by design, and the plan is the reviewable artifact; giving it its
own file read would make the plan depend on tree state the snapshot does not
describe.

## Decision 2 — the INDEX gets a real status, and which one

The demote writes `<topic>/openspec/INDEX.md` describing the returned drafts. It is
a governed markdown document in a governed folder, so it needs a lifecycle status
from the ratified taxonomy. `draft` is the right one: the INDEX describes returned
DRAFT proposals and shares their state, and it is regenerated by the next demote
rather than being a durable record.

Rejected: `record`. That claims immutable-evidence status for a file the next demote
overwrites.

## Decision 3 — the `Proposed by:` line is fixed where it is WRITTEN

`proposal_support.proposed_content` rewrites `Status: staged` into
`Status: draft\nProposed by: <change>`. On a document that already carries a
`Proposed by:` line — which is every document making its second lap — that adds a
second one.

The fix updates the existing line instead. It must NOT be done in the demote's
refresh, and this is the load-bearing constraint of the whole change: the promoted
requirement pins that refresh as *"bounded to the provenance slots and the marked
proposal-element sections, leaving every other byte of that file unchanged"*. That
boundedness is what makes it safe to run the refresh over a fragment a human has
been working in. Deduping a header there would trade a data-loss guarantee for
tidiness, so the obligation goes on the gate that writes the line.

Implementation shape: `proposed_content`'s `Status: staged` substitution becomes
status-flip-plus-authorship where no authorship line exists, and
status-flip-plus-update where one does. The status flip itself is unchanged.

## Decision 4 — the state slot's rendering, and its unavailable case

`plan_demotion` already carries `status_at_demote` from the snapshot. The snapshot
also carries `task_progress` as `{"completed": N, "total": M}` or absent — the
generator returns None both when there is no `tasks.md` and when the file records
zero tasks, and those two cases are indistinguishable downstream and do not need to
be distinguished: both mean "no progress to report".

Rendering: `active — 9 of 22 tasks done`. Prose rather than a code, because the slot
is read by humans in a markdown document, and the existing four slots are all plain
prose values.

Absent progress renders the status alone (`active`), NOT `active — unavailable`. The
promoted requirement's unavailable rule is about a value that could not be
RESOLVED; a change with no tasks has no progress to resolve, which is a different
statement, and writing `unavailable` there would report a lookup failure where there
was none.

**The `DemotionPlan` carries the progress, not the executor.** Same reasoning as
`status_at_demote` before it: the plan is snapshot-derived and pure, and the executor
never sees a snapshot.

## What is deliberately not designed here

- The shallowest-markdown arm of the primary-fragment selection rule. Out of scope
  by Brett's Decision 1 ruling of the same day, deferred until a real topic reaches
  the fallback arm — 0 of 31 do today.
- `corpus.parse_status`'s read-side pseudo-line blindness. Its own change, so
  doc-health's shared reader owns its baseline diff (`align-status-reader-to-real-lines`).
- Any widening of the demote's bounded refresh, for the reason in Decision 3.
