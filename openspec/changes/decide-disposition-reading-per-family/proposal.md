## Why

**THIRTY-ONE ENTRIES IN THE AGGREGATION'S `health/dispositions.yaml` BELONG TO
EIGHT FAMILIES THAT WERE NEVER TOLD WHAT AN ENTRY OF THEIRS MEANS**, and the
sibling packet that answered the question for the ninth family answered it for
that family alone.

`honour-grandfather-dispositions-in-ratified-provenance` (#939, archived
2026-09-11) taught `ratified-provenance` to read a dated, cited entry and
report a matching ARCHIVED finding at `info` carrying its citation. Its
`design.md` D6 named what it was not taking, and its `tasks.md` § 7.2 filed
this issue for it: whether any of the OTHER families' entries should be
downgraded rather than suppressed — or read at all, for the families that read
nothing — **is a separate question about a different subject**.

It is a question with a live population and no default answer. Four of the
thirty-one entries were written on 2026-09-11, the same day the parent
archived, and their own `rationale` fields reason about the mechanism in prose,
in a different repository, because canon does not state it. One of them says it
outright:

> The `proposal-origin` family does NOT read health/dispositions.yaml for ACTIVE
> findings (only the doc-health runner's uncited-resolution arm keys on (family,
> repo, path)), so this row stays visible in the nightly exactly as it is today;
> nothing is suppressed by this entry.

That is a correct reading of the code, derived by a lane that had to read the
code to get it, and it appears nowhere in the contract. **THE REMEDY IS TO WRITE
THE BOUNDARY DOWN, NOT TO BUILD AN ARM.**
