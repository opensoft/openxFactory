# Product Advocate review — `add-wallet-carried-review-authority`

**What's solid, in one line each.** The doctrinal work is genuinely good: reconciling `doc-health`'s "Authority never transfers" by *scope* rather than attribution is the right call and correctly argued; dropping `consent-instrument` as a precedent while keeping it as a named non-precedent is cheap and honest; the custody-registry derivation of the tier ceiling (§2) removes a rule instead of adding one, which is the rarest good outcome in a governance proposal; and quoting the seeded-corpus record's own "anyone citing this for the proposition that seat diversity is unnecessary is citing it wrongly" caveat against its own argument is the behavior you want from every future proposal. The `distinct_holder_constraint_refs` move turns QA 4.2's "no observable" into a validated refusal — that one is a real product improvement, not a rewording.

Four concerns, ranked.

---

## 1. The Why names the bypass; the Out-of-scope section gives it back. Nothing here ends a single `--admin` merge, and the proposal never says which merge goes first.

**Concern** — The problem statement is "every governed merge today takes `--admin`, and a gate whose only habitual discharge is its own bypass is a ritual," but the change explicitly removes no bypass and names no first candidate class that stops needing one.

**Evidence** — `## Why` (proposal.md:44-56) is entirely the sole-developer deadlock. `## Impact` closes with "No existing gate is weakened and no `--admin` bypass is removed by this proposal." `## Out of scope, deliberately` lists "Retiring `--admin` usage on any repository. That is a per-repo policy decision downstream of both this change and the substantive review lane." The floor stands as ratified, so contract bytes, gate/workflow definitions, credential surfaces and security posture remain "permanently human-only regardless of unanimity" — and the only human is Brett. That class covers codexFactory's `hermes/domain/review-councils/gate-rules.yaml`, `.github/CODEOWNERS`, the 35-pattern floor, and the intake register this change proposes to create. Every one of those is a merge Brett will still push with `--admin` the morning after ratification, and the intake register will be among them.

**Impact — HIGH.** The operator ratifies a doctrine, builds a register, issues grants, and his daily merge experience is byte-for-byte unchanged. Worse, the register itself becomes a floor-covered artifact he maintains by bypass — an authority ledger whose own edits are ungoverned. The predictable outcome is not rejection but drift: the register is populated once, then stops being updated, exactly like CODEOWNERS, which the proposal itself identifies as the cautionary precedent (Q3).

**Suggestion** — Add a short section, `## The first bypass this ends`, naming one concrete class end-to-end: candidate class, holder, grant scope, tier, and the enforcement change that makes the merge discharge without `--admin`. The honest candidate is not a governance file — it is the routine-code class `codexfactory-routine-code-clearance` already targets. Make it an acceptance criterion of `review-authority-intake`: *"The capability is not realized until one named candidate class in one named repository discharges its review gate from a grant, with no `--admin`, and the convening record evidences it."* If no such class exists until the substantive review lane's 16 remaining tasks land, then say so in the Why and demote the framing: this change is a **precondition** for ending the bypass, not a remedy for it, and the Why should name the successor that is the remedy plus its trigger. Right now the Why sells a cure and the Out-of-scope quietly returns it.

---

## 2. Cold start is unaddressed and composition-revocation is an unattended tripwire aimed at a one-person shop.

**Concern** — "No wallet, no delegation" is stated as "a real cost, and it is bounded," but zero wallets exist in the family today, there is no key infrastructure, and the one mechanism the proposal calls "free" — composition-hash revocation — will mass-revoke the entire register on a model vendor's release schedule with no reissue path, no notification, and no grace period.

**Evidence** — I verified there is no `openxwallet` record instance anywhere in openxFactory outside `contracts/openxwallet/examples/` (16 example files, zero live). The custody registry says it in terms: "there is no key infrastructure in the stack today" (`openxwallet-custody.registry.yaml`, `holder_readable` notes). §2 of the proposal makes a wallet a prerequisite for holding review authority. Q5 concedes "A council seat casting a GitHub review produces no wallet-signed exercise today." Meanwhile §2's closing paragraph celebrates that a composition change "revokes its outstanding grants at once, with no tolerance band and no grace period" — and `openxwallet-agent-profile/spec.md:27-48` confirms **model version** is a declared component and "WHEN any single component of the declared set changes THEN the change alone is sufficient to revoke." The holders are hosted Claude models. Counting the current councils: `gate-rules.yaml` and `merge-readiness.yaml` name ~6 distinct seats (`company-policy-lead`, `intent_owner_role_slot`, `lead-quality`, `lead-security`, `lead-integration`, plus the CSC conditional) plus 2 councils as bodies — 8 holders, each needing a wallet with a declared custody model, before grant one. Grep for `notif|renew|lapse|bootstrap|onboard|cold start` across the proposal returns nothing; `expires_at` appears only in field enumerations.

**Impact — HIGH.** Day one is a key-management project the proposal does not scope: mint 8 wallets under `holder_readable` (the only realistic model with no key infrastructure), declare 8 composition hashes over six components each, then issue grants per target across 18 submodules. Day two, Opus 5 ships, every composition hash moves, and every grant in the register is revoked simultaneously — silently, because nothing notifies. The operator's rational response is to omit `model version` from the declared component set, which converts the register into the CODEOWNERS failure mode with extra steps.

**Suggestion** — Two additions. (a) A `## Cold start` paragraph: who mints the first wallet, under which custody model, and whether the root issuer of Q2 must itself hold a wallet or is standing-based. If the root is Brett's own standing and needs no wallet, say it — that single sentence removes a circular dependency the bench will otherwise hit. (b) A new open question, `Q8 — What happens when a hosted holder's composition moves?` Pose it with its real exits: a standing reissue policy the intake supports as a first-class act; whether derived grants survive a parent revoked for composition drift rather than for cause; who or what tells the operator the register went empty; and whether the declared component set for a hosted-model holder may pin a model *family* rather than a version. That last one is a real product decision — the current spec makes it a validation failure, so if the answer is "no," the intake needs an operational answer instead, and it should be posed here rather than discovered at the first model bump.

## 3. The intake is called "the genuinely new operational artifact" and is designed entirely in open questions. No MVP is named.

**Concern** — The one piece with no prior art gets a single paragraph of description and seven unresolved questions covering its location, its issuer, its reader, its exercise checkpoint, its proof, its refusal subject, and its election record — which is the whole of its design.

**Evidence** — §4 is roughly 250 words and closes with "Its questions are posed in `## Open questions`, not decided here." Q1 (where it lives), Q2 (who issues), Q3 (what validator reads it), Q4 (exercise checkpoint), Q5 (what an exercise even is), Q6 (refusal subject) and Q7 (election home and role) are the register's entire operational surface. There is no `tasks.md`, which the proposal states up front and does not claim otherwise. The proposal names the risk itself, correctly: "an intake with no reader repeats the CODEOWNERS mistake at higher stakes."

**Impact — MEDIUM-HIGH.** A bench can ratify the doctrine, but nothing shippable follows from it. The realization then arrives as a downstream change carrying all seven decisions, at which point the seam between "the doctrine the bench ratified" and "the register somebody built" is where the drift lives. The specific failure is Q3's: openxFactory gains a second authority declaration that no validator reads, and the operator learns a second time that writing down who may do what changes nothing.

**Suggestion** — Name the MVP in the proposal, in scope. Concretely: *one* file at a fixed path, *one* holder (the `merge-readiness` council as a body), *one* target repository, one act, tier `act`, one `expires_at`, and *one* validator whose only job is to fail when a convening admits a holder with no active row. Everything else — per-project schema election, distinct-holder constraints, digest-disjointness, per-seat grants — is a named successor. Then bind ratification to Q3 rather than deferring it: *"`review-authority-intake` is not realized until the register and a validator that reads it land in the same change."* That is the single cheapest guard against the CODEOWNERS outcome the proposal already fears, and it costs the bench one sentence.

---

## 4. "Recommended but optional, and confers nothing" guarantees the schema is never elected — including for the one property that isn't ergonomics.

**Concern** — The three-repository schema is given ~900 words, is explicitly ruled out of bench scope, is declared to confer no gate, floor, grant or clearance benefit, and has no settled home or deciding role — which makes it a section the bench must read and cannot act on, describing a thing a solo operator will never adopt.

**Evidence** — "The recommendation confers nothing, and this must be stated so it is never read as a soft requirement. Electing the schema changes no gate, no floor, no grant, and no clearance eligibility." Q7 leaves both the recording location and the deciding role open, and honestly flags that the convener's phrase "human project manager" maps to `PM` while the decision content ("where project boundaries sit") belongs to `PA` — posed, not resolved. Yet the same section concedes "One property the schema does buy, worth recording because it is not ergonomics": under a separated assembly plane the review core is foreign to every consumer, so a change to the review machinery is judged under the *prior* constitution.

**Impact — MEDIUM.** Adopting costs three repositories to maintain alone and returns zero governance benefit by the proposal's own declaration; nobody rational elects it, so the prior-constitution property is never realized. That property is not incidental — it is the structural answer to the very self-review problem the floor currently handles by "permanently human-only," which for a sole developer resolves to "Brett, via `--admin`, forever." The proposal identifies the one thing that could shrink the human-only remainder and then decouples it from every incentive.

**Suggestion** — Couple it or cut it. To couple: add one sentence tying the election to the live thread — *"A project whose review machinery is resolved from a pin naming a different repository and a disjoint digest set satisfies prong (ii) of digest-disjointness for that machinery; electing the recommended schema is one way to satisfy it, and the only currently available one."* That gives election something concrete to earn without making it a requirement, and it wires the schema section to the digest-disjointness ruling the bench *is* being asked about instead of leaving them as two unconnected essays. To cut: move the entire section to `ideation/staging/three-repository-project-schema/` as its own topic with its own exit path, and leave a three-line pointer here. Either way, resolve Q7's role question rather than posing it — a recommendation whose deciding role is undetermined cannot be recorded, and `PA` is the answer the ratified Owns/Decides table already gives.

---

**Bottom line for the bench.** The mechanism argument is the strongest part of this document and I would ratify it as doctrine. What I would not do is let it archive as-is, because on the operator's own stated problem it currently returns a doctrine, a register with seven undecided properties, an advisory layout nobody will elect, and a prerequisite (wallets) that does not exist anywhere in the family. Concerns 1 and 3 are the two that decide whether this gets used: name the first bypass that ends, and ship the register with its reader.
