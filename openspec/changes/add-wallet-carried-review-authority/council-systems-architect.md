# Systems Architect review — council seat, 2026-08-22
Subject: `openspec/changes/add-wallet-carried-review-authority/proposal.md`

## Concern 1 — The one boundary has no candidate-side input, and every path to one re-enters the checked tree (HIGH)

**Evidence.** §3 states the rule as "a council MAY NOT be convened over a candidate that touches the machinery that council is assembled from," issued at `admit_layer_convening`. But the runtime is blind on both sides of that predicate:

- `admit_convening` (`/home/brett/projects/xFactory/installs/hermes-install/src/hermes_install/domain/council_orchestration.py:256-318`) reads exactly three keys from the posted block: `council_id`, `subject_pin`, `mix_id`. `packet_refs` is never read. There is no diff, no changed-path set, no repo handle.
- The block is *constructed by the checked tree*: `/home/brett/projects/xFactory/xFactories/codexFactory/.github/workflows/council-lane-reusable.yml:473-478` builds `{"council_id": …, "subject_pin": head_sha, "packet_refs": [pr-url, commit-url]}`, with an in-file comment that "a malformed packet ref never fails a commission (the council reads packets; it does not depend on their syntax)."
- Q6 poses only the *M* side ("what is the machinery this council is assembled from"). The candidate side — "what does this PR touch" — is never posed, and ## Impact's downstream list names "the runtime non-self-review refusal … (Q6)" without naming its input.

So the refusal requires either (a) the lane telling the runtime the changed-path set — a self-report from a workflow file the candidate PR can edit in the same PR, which is strictly weaker than the in-tree floor it improves on; or (b) the AKS runtime fetching the diff itself, which needs a GitHub credential per governed target held by Hermes, egress from the cluster, and a per-target machinery map. Neither is costed anywhere.

Worse, both of Q6's proposed handles under-cover the machinery. The domain content set (`domain_content_set.py:37-47`) is `escalation-rules.yaml`, `agent-mixes.yaml`, `memory-boundaries.yaml`, `practice-catalog.yaml`, `roles/`, `policies/`, `review-councils/`. `scripts/` — "the decision core's whole import root," the surface LS-A3's `scripts/yaml.py` attack actually used — is not domain content and never will be. The runtime refusal, fully built, would not have caught the one attack that has been executed. Note too that the floor's own declared source of truth is `hermes/domain/review-councils/records/2026-07-23-gate-rules-nightly-sweep-clearance.md` (`add-substantive-review-lane/specs/roles-authority-model/spec.md:328-333`), a `.md` file that directory-kind loading (`*.yaml` only) never materializes.

**Impact.** HIGH. The spine's structural claim is unbuildable as scoped. If the specs phase adopts option (a), the family adopts a refusal whose trusted input is candidate-supplied — the exact "control adopted on a description of an enforcement" that LS-A3 exists to forbid.

**Suggestion.** Add Q6b: *what is the candidate-side predicate, who computes it, and where does that computation live?* Then constrain the answer: the changed-path set must reach the runtime by a path the candidate cannot author — realistically Hermes pulling the diff under its own credential, keyed off `subject_pin` (which is already `head_sha`) plus a target-repo identity the runtime holds, not one the job posts. And state plainly in §3 that the refusal's reachable subject is the *materialized domain content only*, so codexFactory's `"scripts/**"` floor entry, its CODEOWNERS line and the import-root test remain the sole defence for the decision core — the runtime refusal is additive, not a replacement.

## Concern 2 — There is no checkpoint that is both outside the tree and permitted to enforce (HIGH)

**Evidence.** Q4 asks where revocation is checked; Q5 concedes "a council seat casting a GitHub review produces no wallet-signed exercise" and offers two exits. Both exits fail architecturally:

- *Exit A (name a signing point in the convening flow).* The only out-of-tree component is the Hermes runtime, and its ratified capability forbids it from enforcing: "A recorded verdict is advisory evidence only … SHALL derive no approval, merge, dispatch, or any other state transition beyond the job's own resolution from any verdict" (`/home/brett/projects/xFactory/installs/hermes-install/openspec/specs/council-orchestration/spec.md`, third requirement). Enforcement is deliberately consumer-owned by codexFactory's `council_clearance._verdict_valid` — in the checked tree. So a grant checked at the moment of enforcement lands back inside the tree, in the same class of code as LS-A3. Making the runtime enforce needs a MODIFIED delta on `council-orchestration` that inverts its advisory-only requirement — a much larger act than "downstream realization."
- *Exit B (grant recorded, exercise evidenced by the existing audit trail).* This is self-negating under the ratified vocabulary. `contracts/openxwallet/openxwallet-grant-exercise.schema.yaml` requires `proof_of_possession`, `attribution`, `custody_model_in_force`, `revocation_check`, `event_class` with `additionalProperties: false`. An exercise with no wallet signature is `event_class: unauthenticated_request` and `unattributed` — and `openspec/specs/openxwallet/spec.md` rules that such an act "is not assigned to a holder" and that "no authority is conferred by presentation alone." A grant whose every exercise is unattributed confers nothing checkable. That is not a declared deviation; it is a grant that is documentation — precisely the CODEOWNERS failure Q3 warns against, at higher stakes.

There is also no substrate: `grep` across `openxFactory/scripts/`, `installs/hermes-install/src/`, and `codexFactory/scripts/` + `hermes/` returns zero wallet code and zero `xfactory_wallet_grant` instances outside `contracts/openxwallet/examples/`. openxwallet is contract-only, never instantiated. The custody registry says so in terms: "there is no key infrastructure in the stack today" (`contracts/openxwallet/openxwallet-custody.registry.yaml:53-58`).

**Impact.** HIGH. Without a resolution, "authority travels in grants" cannot be *checked* anywhere in the merge path, and the intake becomes a register nothing reads.

**Suggestion.** Make Q5 a gating question rather than a posed one, and add a third exit that is actually buildable: mint the seat's wallet key inside the council-deliberation job, have the runtime verify the signature over the seat return at **verdict conformance** (`check_verdict`, which the runtime already owns and already refuses fail-closed), and record the exercise there. That keeps the check out of the checked tree without touching the advisory-only requirement, because refusing a *malformed verdict* is already the runtime's job. If that is not taken, state explicitly that Exit B yields `unauthenticated_request` exercise records and therefore confers no checkable authority — do not let it pass as a deviation.

## Concern 3 — Revocation-at-exercise is unsatisfiable by either Q1 option, and composition-revocation is an availability trap (MEDIUM-HIGH)

**Evidence.** `openspec/specs/openxwallet/spec.md` requires "A capability consuming grants SHALL check revocation at exercise rather than trusting issuance," with the scenario rejecting issuance-time validity as evidence of current validity. Q1 offers exactly two homes for the register: "canonical neutral register with per-target rows, or neutral schema with per-repo instances." Both are git files, and every distribution path in this family is digest-pinned and lagging — `stack.yaml` pins the openxFactory version; layer content is fetched by digest pin and sha256-verified fail-closed (`lifecycle/seed_layer_content.py:1-21`). A materialized or pinned register *is* an issuance-time snapshot; a revocation would take effect only at the next re-pin and re-seed, a human lifecycle act. Neither Q1 option can satisfy the requirement it is subject to. The conforming shape is a live lookup, which nothing in the family provides and which contradicts content-addressed pinning doctrine.

Two compounding effects the proposal does not carry:

- **Composition revocation is framed as a free bonus; it is an outage mode.** `openspec/specs/openxwallet-agent-profile/spec.md` revokes on *any single component change*, "no tolerance band and no grace period," with the component set including model version and retrieval corpus. A provider-side model rev, or a retrieval corpus defined as the repository at HEAD, revokes every reviewing seat mid-lane. Re-issuance requires the root issuer — Q2, undecided, but for a sole operator that is Brett. The gate that today discharges by `--admin` would then discharge by "grants revoked, human re-issues": the same ritual with more steps.
- **The distinct-holder constraint is not yet the observable that supersedes QA 4.2.** `contracts/openxwallet/openxwallet-distinct-holder-constraint.schema.yaml` fixes the comparison basis as "the PRIOR ACT'S RECORDED HOLDER — what the exercise record for that act actually carries." Enforcing it requires a queryable exercise-record store keyed by (object, act). None exists. That answers the scale question directly: at many holders × targets × grants there is no lookup path, no index, no cache and nothing to invalidate, because there is no store.

**Impact.** MEDIUM-HIGH. The realization phase discovers it must build a live grant/revocation service plus an exercise ledger before a single grant can be exercised — work an order of magnitude larger than "the intake register and a validator."

**Suggestion.** Add Q1c as a real option — a live revocation surface on the Hermes runtime, which already holds Postgres, layer identity and the job lifecycle — and state in Q1 that the two file-based options cannot satisfy the at-exercise requirement. Bound the composition set explicitly for reviewer holders (declare the retrieval corpus as the *pinned* seat prompt + ontology package, never the candidate repo) and require a pinned model version, so composition churn is a governed act rather than a provider event.

## Concern 4 — The "already provides it" premise is not live today, and "no new schema" will not hold (MEDIUM)

**Evidence.** §3 leans on the runtime materializing codexFactory's `review_council` content. It does not, on the trees I read:

- codexFactory's `/home/brett/projects/xFactory/xFactories/codexFactory/hermes/domain/content-manifest.yaml` (commit 135f761, 2026-07-29) declares `content_set:` with **only** `domain_ontology`. Under `_load_declared_set`, a manifest-bearing archive loads "EXACTLY its declared set," so `review_council` would never materialize even on a successful seed → `admit_convening` raises `CouncilContentUnseededError` for every convening.
- Worse, the runtime's `CONTENT_KINDS` frozenset (`domain_content_set.py:40-53`, last touched 2026-07-24) is the seven pre-ontology kinds. `domain_ontology` is not among them, so `_manifest_locations` refuses with "unknown content kind: domain_ontology" and the whole archive fails to seed pre-write. openxFactory's neutral `contracts/hermes-domain-overlay/content-manifest.schema.yaml:45` ratified `domain_ontology` as additive; the consuming runtime never learned it, and there is no open change in hermes-install adding it. That is a live contract/runtime drift.

The proposal cites the *schema* (`content-manifest.schema.yaml:37`) and the *example* (`examples/hermes-domain-content-manifest.example.yaml:9`) for the `review_council` mapping — not codexFactory's actual manifest. That is the LS-A3 shape reproduced in the very section that invokes LS-A3.

On schema: §"One capability, and why no schema" is right that the *grant* needs no new schema, but the change nonetheless implies at least two contract shapes. The convening block needs a candidate-side field (Concern 1) — a change to the posted job envelope, and `neutral-job-envelope` is an openxFactory capability. And the intake register needs a shape the moment Q3's validator exists; a register with a reader is a schema by definition. The rule-of-three argument covers the delegation instrument, not the register.

**Impact.** MEDIUM. Not fatal to the spine, but the bench would be ratifying "the runtime already provides it" against a runtime that currently refuses to seed the domain at all.

**Suggestion.** Verify the deployed AKS build's `CONTENT_KINDS` before the bench rules, and either way add to ## Impact a named prerequisite: codexFactory's `content-manifest.yaml` must declare `review_council` and `deliberation_mix`, and hermes-install must admit `domain_ontology`. Restate §3 as "the runtime provides the *place* for this refusal; the content is not seeded there today." And soften the no-schema conclusion to "no new *grant* schema," naming the job-envelope field and the register shape as declared successors rather than absent.

---

**Overall.** The reshape from topology to wallet-carried authority is the right architectural call — it composes with the single-reviewing-home model, reuses a ratified vocabulary rather than forking one, and gets the custody ceiling for free. The proposal's self-awareness is genuinely high: Q3, Q4 and Q5 name three of the four hard things. What it does not have is the fourth — that after the reshape, *every* enforcement point it needs is either inside the checked tree or forbidden from enforcing — and that gap is what turns Q4/Q5 from open questions into a blocking design decision. My recommendation is to rule on Q5's exit before the specs phase, not after.
