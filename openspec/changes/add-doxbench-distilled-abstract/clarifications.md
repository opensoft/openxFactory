# Clarifications

_Captured during proposal council review. These constrain the design._

_Generated by /opsx:propose council on 2026-08-25_

## Council-Identified Constraints

### The abstract cache must not be the chat TurnStore

**Raised by:** systems-architect

**Concern:** Ruling 1's recommendation reuses `TurnStore`'s shape, and the
obvious implementation reuses the INSTANCE. It cannot. There is exactly ONE
`TurnStore` per served process (`scripts/ideation_dashboard/serve.py:4796`,
whose own comment reads "ONE fresh turn-idempotency ledger per served process"),
and it is bounded at `MAX_IDEMPOTENCY_ENTRIES = 64` entries and
`MAX_IDEMPOTENCY_BYTES = 16 MB`
(`scripts/ideation_dashboard/doxbench_turns.py:998-999`). Abstract generation
over a large scope would churn through that bound and EVICT the chat turns'
idempotency records, so a chat retry that should replay would re-dispatch.
Separately, the store refuses a different digest under the same key as a
conflict rather than replacing it (`doxbench_turns.py:1033-1069`), so an
abstract cache keyed on document path alone would hard-refuse every regeneration
after a document edit.

**Design impact:** A SEPARATE, separately-bounded store, never the chat
instance. The key MUST include the digest — `(document path, content digest)` —
so a regeneration after an edit is a new key rather than a conflict. The design
needs an explicit eviction/re-dispatch scenario at scope scale: a 200-document
scope exceeds a 64-entry bound by more than 3x, so eviction is the normal case,
not the edge case, and re-dispatch after eviction must be stated as expected
behaviour rather than discovered as a cost.

### There is no path from a good abstract to a better document

**Raised by:** product-advocate

**Concern:** The abstract is terminal. A reader who sees a model-derived
abstract that is plainly better than the document's own `Summary:` header — the
single highest-value case this feature has, per the Why section's measurement —
has nowhere to go with it. Every route out of the pane is manual retyping. The
feature improves what a reader SEES without ever improving what the corpus
HOLDS, which means its value evaporates the moment the pane closes and must be
re-earned by another model call next time.

**Design impact:** The design MUST state the promotion affordance's ABSENCE as a
deliberate boundary rather than leaving it unmentioned, and MUST name where a
future "propose this as the document's `Summary:`" verb would attach — the
existing chat-proposal-plus-Apply-plus-gate path recorded as Option B′ in the
proposal's Alternatives. Naming the attachment point now is what keeps the
read-only slice from becoming an architectural dead end. Nothing in this slice
may write a `Summary:` header.

### Prioritization against the operator's still-open list

**Raised by:** product-advocate

**Concern:** The operator's open findings list carries a P1 — per-key storage is
unforwarded, so a reload destroys unsaved buffers — plus four P2s, all of them
ahead of annotations 2 and 3 that this change serves. Building a new model-backed
surface while a data-loss defect stands is a prioritization inversion, and a
proposal that does not say so invites one by silence.

**Design impact:** Neither the design nor the tasks may schedule this work ahead
of the standing P1 and P2 items without Brett's explicit say. If this change is
split under ruling 0, the doc-only half is genuinely cheap and can proceed
regardless — it removes a falsified requirement rather than adding a surface —
but the model half should be sequenced behind the open defects.

### The hosted plane's real problem is determinism, not wording

**Raised by:** adversary

**Concern:** The first draft treated the hosted read-only plane as a CAPTIONING
problem, solved by an honest "no distillation available on this plane" note. The
wording is fine. The actual problem is that ruling 2(a) would project a
model-derived value into a snapshot whose contract requires byte-identical output
from an unchanged tree (`openspec/specs/ideation-dashboard/spec.md:7`), onto a
plane that structurally cannot regenerate it
(`spec.md:1046` — "the hosted/read-only plane MUST offer neither route").

**Design impact:** Recorded as SETTLED in the proposal, not deferred: ruling 2(a)
is withdrawn as a declared evolution and re-declared as a separate future change
that must first amend `:7`'s byte-identical scenario. The caption wording stands
as proposed. The 2(b) cost — two consoles at one (repository, ref) may show
different abstracts — is recorded in the proposal rather than hidden.

### Verifier coverage needs hand-written fixtures and RED cases

**Raised by:** systems-architect

**Concern:** `FakeWorkbenchModelPort.dispatch` returns a CONSTANT —
`{"assistant_prose": "fake grounded answer", "proposals": []}`
(`scripts/ideation_dashboard/doxbench_model.py:1101`) — so a verifier test run
against the default fake proves only that the happy path does not crash. No
coverage of a dropped topic, a wrong-document abstract, or a leaked neighbour
path comes for free.

**Design impact:** Every verifier test seeds its own `dispatch_result`, and the
suite MUST include RED cases per refusal class: an abstract that mentions no
declared topic, one naming a path absent from its request, one naming the wrong
subject. What IS cheaply falsifiable is the PROMPT rather than the response — the
fake records every envelope on `port.dispatched`, so the one-subject-only rule
and the byte-identical-envelope requirement are testable with no model at all,
and those tests should carry the weight the response-side tests cannot.
